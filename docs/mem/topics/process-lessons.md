## 先架构后编码
- 2026-09-06 原话锚点："我们应该先讨论好整体架构和技术栈，再去做详细编码"。**改/造东西前先对齐整体设计与技术栈，别急着写实现**；有歧义就把歧义摆出来问。

## 别绕主线另起炉灶 / 别把简单事讲复杂
- search 工具教训（9/7）：用户要的就是"给模型一个 search：游戏名进去、问题进去，泛问拆词=写好 prompt 交给 LLM 自己拆"；我却设计成引擎教模型拆关键词的复杂管道 → 被斥"为什么要搞这么复杂"。**能用一个直白工具解决的，别造一个系统。**

## 复用 = 搬真逻辑，不是借壳
- "复制爬虫再改造" = 把毕设**本来就适用**的稳法搬进来（版面翻页+去重、点赞门槛、schema、URL 拼装），不是只借 `_launch_browser`/`_login` 然后别的全新写。交代血缘精确分层（字节复制 / 继承哪些 / 新写哪些），被翻旧账认账改口不狡辩。（feedback-code-provenance）

## 考虑所有情况（安全/边界类）
- 权限/边界/校验需求：先列身份矩阵（未登录/普通用户/内部角色），再列绕过向量，逐一验证。**优先结构性防线**（工具按身份根本不暴露），不是 prompt 劝告。

## 诚实口径
- 不装平衡（某平台无声就明说）、不撒谎、编不出就说编不出；数据量级/结论可溯源；"数据是死的但够用"这类判断要有实据，别让修链路变成无底洞。
