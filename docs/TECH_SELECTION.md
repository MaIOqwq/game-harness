## D1 编排层：手写 function-calling 循环 vs LangGraph vs 其他 Agent 框架

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. 手写 function-calling 循环**（现状 ✅） | 引擎里 `for rnd in range(6)`：把 tools 白名单交给模型 → 解析调用 → 执行 → 循环，状态守卫内联在每轮 | 状态守卫（46 开/冷却/护栏）与业务紧贴、逐行可见可测；无框架黑盒；依赖面最小、去敏发布最干净；单循环心智负担低 | 需要自己写循环骨架/超时/重试；多分支复杂编排要自己维护（当前不存在） |
| **B. LangGraph**（客服项目已验证） | 图化编排：StateGraph 节点 + 边 + checkpoint | 图可视化/调试、checkpoint 时间旅行、多 agent/HITL 是生态最强；面试可讲 | 本需求是**单 gather-then-compose 串行流**，几乎没有可并行的图分支；checkpoint/时间旅行当前无对应需求；图会把散布的守卫拆散到节点间，反而藏逻辑；多一层依赖 |
| **C. LangChain AgentExecutor / create_react_agent** | 现成 ReAct 跑环 | 开箱即跑 | 抽象层厚、版本变动大；定制守卫（46 开/断路器）要透过框架钩子，难审计 |
| **D. AutoGen / crewAI** | 对话式多 agent 框架 | 多 agent 协作开箱 | 本需求单 agent 足够；多 agent 是方案不是需求；心智与调试成本更高 |
| **E. 现成 harness（deepseek-harness 等）** | 直接用别人写好的 harness | 少造轮子 | 产品定位就是"自己做 harness 学习+展示"，直接用则失去本项目的骨架意义；定制深浅取决于别人的抽象 |

**结论：A 手写循环** ✅（现状即 A，但理由独立成立）
1. 需求是**单问句 → 多轮 gather → 收口作答**的线性 flow，无并行/竞争/多 agent 场景——框架的差异化能力（图/时间旅行/Studio/多 agent/HITL）当前全部没有对应物。
2. 项目最重的复杂度在**门控状态机**（断路器/冷却/配比/护栏），它们散在"每轮要不要继续爬"这个决策点上。手写让守卫是引擎的一部分，能单测、能审计；换成框架等于把守卫拆成节点间隐式状态。
3. 技能不亏：LangGraph 已在客服项目实操并上简历，此处不需要再用一次来证明。
4. 依赖与发布最干净（标准库 + requests 级）。
**触发更换**：若演化出真正的多 agent 竞争编排、需要 checkpoint 回放做调试、或节点分叉超过手写可控阈值（约 >10 个独立状态位）→ 评估 B。

## D2 推理模型：DeepSeek vs 其他商用 LLM

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. DeepSeek-chat**（现状 ✅） | API 对话，function-calling 原生 | 中文语感好（处理社区口语/黑话语境有优势）；API 便宜（多轮爬取 + judge 反复调用成本敏感）；function-calling 规范 | 外部依赖（有 key 才能跑；无 key 走 mock/存档-only 降级）；上下文与推理能力受模型上限约束 |
| **B. 通义千问 Qwen** | 阿里商用 API | 中文强、生态稳 | 需独立 key；功能与定价略近但未见必需优势 |
| **C. Claude** | Anthropic API | 推理与长上下文强 | 单价更高；中文社区语感不是长板；成本敏感场景不利 |
| **D. 本地小模型** | 本地推理 | 无网络依赖、隐私 | 单机/内网机器算力不足支撑反复多轮；质量与可控性差距大，本期无必要 |

**结论：A DeepSeek 默认** ✅
1. 需求是**中文游戏社区口语/黑话语境** + **高频工具往返**：DeepSeek 中文语感与低成本组合最贴合；cost-per-round 是反复 judge/多轮爬的核心约束。
2. 依赖已抽象成单一开关：密钥在环境变量，`/api` 形态是标准 OpenAI-compatible function-calling，**换 provider 只改一个常量 + base_url**，不锁定。
3. 降级路径已设计：无 key/超时 → mock 数据源 + 存档-only，demo 不断。
**触发更换**：judge 等高一致性场景若 DeepSeek 达标率不足 → 只对那一个角色切换更贵模型（分层模型策略），不全局动。

## D3 存储：SQLite vs PostgreSQL vs MySQL vs 纯文件

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. SQLite**（现状 ✅） | Python 标准库内置，单文件 | **零安装零依赖**，随项目走（别人 clone 即可跑）；单文件好备份/迁移；SQL 能力对本期够用；harness 开源界主流（LangGraph AsyncSqliteSaver、DeepSeek Harness 双持久化都带 SQLite） | 单写者模型（单用户无压力）；不适合并发写很多/多机共享 |
| **B. PostgreSQL** | 独立服务 | 并发/扩展性强、生态大 | 需安装/常驻服务；对单机 demo 是负资产；部署与去敏发布都要带起来 |
| **C. MySQL / MariaDB** | 独立服务 | 团队熟、运维文档多 | 同上；在 生产服务器/演示服务器 已有现成 MySQL（毕设），若上线同机共存可复用运维 |
| **D. 纯 JSON/JSONL 文件** | 直接落文件 | 极简、可人读 | 查询/去重/版本化全要自己写；跨话题检索麻烦；DeepSeek Harness 用 zstd+SQLite 双写而非纯 JSONL 正因如此 |

**结论：A SQLite** ✅
1. "别人下了咋用？"——这是硬需求：**免安装**。Python 自带 `sqlite3`，clone 即跑，是 demo 与 GitHub 发布的最佳契合。
2. 量级远未到瓶颈（单会话几十~几百条，月级累计数千条）；去重/检索用 SQL 即可。
3. 已封层：`db.py` 统一 `connect/init` + `HARNESS_DB` 换路径，**换 MariaDB/PostgreSQL 只改驱动层**（毕设已具备 MySQL 运维，真有线上化再切不迟）。
**触发更换**：需要多机共享/高并发写，或单库超过约十万行且 SQL 检索开始吃力 → 切 PostgreSQL（或线上复用 MySQL）。

## D4 检索与证据召回：关键词/SQL 检索 vs 语义向量库 vs FTS5

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. SQL 关键词按话题/时间检索**（现状 ✅） | L3 `observation` 存 verbatim 原文，`search_archive` 按话题命中回捞 | **可溯源**：召回的是原文，能直接 `[id=N]` 引用；零依赖；对"快照内 + 按话题命中历史"的量级足够 | 语义近义召回弱（"膨胀神游"类黑话要靠 L4 映射补，不是靠向量） |
| **B. 语义向量库（ChromaDB / pgvector）** | 向量召回近义内容 | 语义召回强 | 又要安装/服务/embedding 成本；召回的"相似句"不是原文，**引用链变脆**（本项目数据精准度最高约束下风险大）；曾踩过 ChromaDB WHERE 后过滤缺陷（RAG v2 教训：3/65 召回） |
| **C. FTS5 全文索引** | SQLite 自带全文索引 | 在 A 之上加词法权重/子串命中，无需外部依赖 | 仍是词法不是语义；本期 A 已够，FTS5 是 A 的自然升级 |
| **D. 全量证据塞进 LLM** | 不做显式检索 | 简单 | 上下文爆（精准档上万 token 证据），违反 IN_CEILING 治理模型 |

**结论：A 关键词检索为主，召回缺口出现再考虑 FTS5 → 向量** ✅
1. 本期检索发生在两处：**本轮采集的快照内**（gather 直接引用，不需要"检索"）与**历史话题回捞**（数量有限、主题明确）。词法命中 + L4 别名映射已覆盖；语义向量对这两处都没有不可替代的价值。
2. 本项目第一约束是**证据可溯源**；向量召回"相似的二手句"会稀释原文证据，与 `[id=N]` 引用契约冲突。
3. RAG v2 的既有教训（向量库过滤缺陷）说明**在没出现明确召回缺口前不预埋向量层**。
**触发更换**：历史语料跨会话语义长尾查询开始明显漏召回 → 先上 FTS5（零依赖）；仍不够且证据溯源有解（保留原文锚点）→ 再评估向量。

## D5 反讽/情感分析：训练专用小模型 vs 纯 LLM judge vs 规则

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. LoRA 双头小模型 + LLM judge 复核**（现状 ✅） | StructBERT LoRA：head_emotion 连续分 + head_sarcasm 可疑门；可疑样本批量交低温 judge 确认；服务挂→关键词法降级 | 成本最优（可疑样本只是少数）；延迟低可内联爬取；**贴合岗位"LoRA/微调"叙事** | 需人工标注（已标 400）+ 蒸馏集；评测当前不达标（情绪 Spearman 0.389 / 反讽 F1 0.368，瓶颈=标注噪声）→ 故**只当软信号，不进硬判定主链** |
| **B. 纯 LLM judge** | 所有样本交 LLM 判 | 零训练、精度上限高 | token 成本随样本量线性涨（一期可能批量 >1000 条，judge 一次 40 条封顶也不够）；延迟高；把窄任务的全量判断压在贵模型上不经济 |
| **C. 规则/词典** | 关键词/句式规则 | 零成本 | 反讽阴阳本质靠语境，规则召回差、误报高（早期试过不够用） |

**结论：A 小模型软信号 + 可疑交 judge 复核** ✅（训练与部署均已完成，但接入严格按"软信号"铁律）
1. 分工合理：**便宜的小模型做粗筛，贵的 judge 只复核可疑少数**——这是成本与精度折中的标准解。
2. 判定安全边界：评测未达标前，任何模型输出都**不驱动硬结论**（`argmax` 负面/概率口径），只做提示性软信号 → 即使 A 精度有限也不污染答案。
3. 独立于模型的岗位价值：完整走通"数据 → 标注 UI → LLM 蒸馏 → LoRA 训练 → 评测 → 部署 → 降级"闭环，这是能讲的故事。
**触发更换**：gold 评测达标（阈值另定）后评估是否升硬判定；若标注扩容跟不上，重估 B 作为主判、A 作预筛的反向组合。

## D6 HTTP 服务/网关：标准库 http.server vs FastAPI

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. 标准库 http.server**（现状 ✅，greeting-web / 爬虫工具同款） | `ThreadingHTTPServer` + 同源 `/api/*` | **零依赖零安装**，clone 即跑；对少量同源 API 够用；已在本项目多个工具验证 | 无 async/自动 OpenAPI/中间件生态；高并发或多路由时手写样板多 |
| **B. FastAPI + uvicorn** | async 框架 | OpenAPI 文档、async、中间件、生产级；爬虫工具当前用 8770-8772 形态但**服务是现成的 HTTP 常驻** | 引入依赖与启动复杂度；对"单用户问答 + 少量 /api"是大炮打蚊子 |
| **C. Flask** | 经典 WSGI | 简洁、文档多 | async 弱；生态整体被 FastAPI 超过 |

**结论：A 标准库起步** ✅（**但这是当前规模下的结论，不是信仰**）
1. "别的人下了咋用"再次是硬约束：标准库 = Python 自带，`python server.py` 就起来，无 `pip install` 门槛——与 SQLite 同理。
2. 问答主链是**同步编排**（一轮爬 60s+），HTTP 层只是壳，async 收益小。
3. 结构已预留：/api 路由集中在一个模块，**切 FastAPI 时静态路由 + 三个端点平移即可**。
**触发更换**：上线公开演示/多用户并发、需要 OpenAPI/限流中间件、或问答改流式输出（SSE 想借用 FastAPI 生态）→ 平移到 B。

## D7 前端：vanilla 单页 vs React/Vue SPA ⏳ 待拍

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. vanilla HTML/CSS/JS 单页** | 零构建单文件 + 现成图表库 CDN | 零构建、可脱敏单文件发给别人；与作者已有 demo（greeting-web/毕设大屏）心智一致；无依赖锁 | 状态多（会话历史+聊天+图表）时手写 DOM 管理累；图表交互复杂时难维护 |
| **B. React/Vue SPA** | 组件化 + 构建 | 组件/状态管理/图表生态强，适合长期演进 | 引入 node 构建链，clone 后要先 `npm install`；对单页 demo 是额外门槛 |
| **C. 现成聊天 UI 组件库** | 复用别人聊天界面 | 上手快 | 定制（结论置顶/卡片图/双模式控件）要绕；样式与需求不贴 |

**设计已定（非此层待拍）**：左侧会话历史 / 右侧聊天栏，聊天栏内嵌图表；卡片式逐张出图；结论置顶；共享时间轴减出图量。
**09-12 新增前端口径**（需求见 `docs/PRD.md` FR1 / FR7 / FR8 / §8 #7#10，此处只记对"选型"的影响）：
- **爬虫状态指示灯两盏**（服务在不在 / 登录态有没有效）→ 需要**轮询 `/health` + 展示三态**，是 A 手写 DOM 最容易吃力的"持续状态"，也是 B 的第一个候选触发点；
- **bili 扫码面板 / NGA cookie 更新引导** → 需要**图片轮询 + 引导式多步交互**，同样是状态机而非静态页；
- **按需出图 + 口径标注**（有软信号=全量分布；无=被引证据分布并标"样本 = 被引证据 N 条"）→ 图表出现的条件性变多，但仍属单页可控。
- 结论：这三条**不改变"先 A 出原型"的判断**（都还没到组件化收益 > 构建门槛的量级），但把 B 的触发条件说得更具体了。
**结论：⏳ 待拍，倾向先 A 出原型**——真实跑通一轮"问→答→图"后，若图表/会话交互复杂度上来再评估 B。此决策等前台动工时定（PRD 打开问题 1），不进本期代码。

## D8 部署形态：systemd vs Docker vs 裸进程

| 方案 | 说明 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. systemd 常驻**（现状 ✅：nga/bili/nlp-tool 已这样跑） | 服务文件 + 开机自启 + 日志 | 与既有采集服务一致；内存可控、单机零额外层；日志用 journald | 换机环境要重配 |
| **B. Docker 容器** | 镜像自包含 | 环境一致、分发复现强 | 内网采集机资源紧（2h4g/4c8g），再叠容器栈是负资产；本期无多机复现需求 |
| **C. 裸进程 + nohup** | 最简单 | 零配置 | 无守护/自启/崩溃重启，不适合常驻 |

**结论：A systemd** ✅（现状延续，理由独立成立：单机常驻、资源紧、与采集服务同运维口径）。发布用"可去敏一键跑的说明 + 服务文件模板"而非镜像。**触发更换**：要给第三方"一条命令复现整栈"、或上云编排 → 补 Dockerfile（结构已留口）。
